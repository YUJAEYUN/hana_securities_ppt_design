# 0. 요구사항과 설계 결정

## 사용자에게 예상되는 최종 요청

단순한 PPT 한 개 제작이 아니라, 반복 사용 가능한 `hana-ppt-skill`을 저장소에 구현하는 작업이다. 구현 범위는 다음을 모두 포함한다.

1. 기존 PPTX에서 색상·폰트·위치·크기·반복 요소를 추출한다.
2. 추출 결과를 사람이 읽는 문서와 기계가 읽는 설정으로 동시에 만든다.
3. 외부에서 만들어진 PPT 초안을 대표 슬라이드 유형의 하나증권 스타일로 다시 구성한다.
4. 생성 결과의 브랜드 이탈과 텍스트 과밀을 자동 검사한다.
5. 사람이 확인할 정성 체크리스트와 제한적인 수정 반복 절차를 제공한다.
6. Claude Code와 Codex에서 같은 로컬 Python 도구를 실행할 수 있게 한다.
7. 첨부된 PPTX 또는 외부 에이전트가 만든 구조화된 초안을 입력받아 디자인만 적용하거나 하나증권식 말투까지 다듬는다.
8. 범용 조사, 사실 수집과 초안 작성은 이 스킬의 책임에서 제외하고 상위 에이전트가 먼저 완료하게 한다.

## 설계 결정

### 지침의 단일 원본

`SKILL.md`를 정본으로 사용한다. `AGENTS.md`는 Windows와 Git 호환성이 불안정한 심볼릭 링크 대신 생성 스크립트 또는 검증 테스트로 동기화한다.

- `SKILL.md`: 스킬 트리거와 실행 절차의 정본
- `AGENTS.md`: 저장소에서 작업하는 Codex용 보조 지침
- `agents/openai.yaml`: Codex의 표시 이름, 설명, 기본 프롬프트
- 동기화 검증: CI 또는 로컬 테스트에서 두 문서의 공통 본문 불일치를 실패 처리

두 도구의 인식 형식이 다르므로 파일 전체를 바이트 단위로 같게 만들지는 않는다. 공통 지침 본문만 하나의 원본에서 생성하는 방식으로 해석한다.

### 브랜드 단일 진실 공급원

승인 후 실행 중 브랜드 값의 정본은 `assets/brand.json`뿐이다. 승인 전에는 `assets/brand.candidate.json`을 분석 후보로만 관리하며 생성 성공의 근거로 사용하지 않는다. `design-tokens.md`는 사람이 검토하기 위한 파생 문서다. 생성기 코드나 레이아웃 문서에 hex 값과 폰트명을 중복 하드코딩하지 않는다.

### 레이아웃 표현

SVG 중간 표현이나 웹 프리뷰 계층은 두지 않는다. 레이아웃 규칙은 `layout-patterns.md`에 설명하고, 실행 가능한 좌표는 생성기 함수와 `brand.json`의 공통 치수 토큰으로 관리한다.

### 하나의 후처리 스킬, 두 워크플로

`hana-ppt-skill`은 범용 PPT 생성기가 아니라 하나증권 스타일 후처리기다. 새 발표자료를 처음부터 요청받으면 상위 에이전트가 필요한 자료를 조사하고 범용 PPT 생성 능력으로 초안을 만든 뒤 이 스킬을 호출한다. 이 스킬 자체는 외부 사실을 검색하거나 출처를 새로 구성하지 않는다.

- `restyle-only`: 문장, 수치, 고유명사와 표·차트 데이터를 잠그고 하나증권 디자인만 적용
- `hana-refine`: 제공된 초안의 사실과 근거를 유지하면서 제목, 문장, 정보 계층과 디자인을 하나증권식으로 개선

말투나 내용 정리 요청이 불명확하면 `restyle-only`를 기본값으로 사용한다. 말투, 제목, 요약 또는 흐름 개선이 명시되면 `hana-refine`을 사용하고 변경 계획을 먼저 확인받는다. 입력 초안이 없으면 이 스킬을 바로 실행하지 않고 상위 에이전트에 초안 생성을 요청한다.

모든 워크플로는 `deck_spec.json`을 장기 정본으로 사용한다. PPTX, PDF와 PNG는 정본에서 생성되는 배포 산출물이며 사용자가 PowerPoint에서 직접 편집하는 것은 목표로 하지 않는다. 이후 변경은 사용자가 AI에게 요청하고 AI가 정본을 수정해 전체 산출물을 다시 생성한다. 제공된 초안 안에서의 말투와 구조 판단은 에이전트가 담당하고 PPTX 읽기·생성·검사는 벤더 중립 Python 스크립트가 담당한다.

초안 인수 계약은 `references/upstream-handoff.md`에 정의한다. 최소 입력은 PPTX 또는 `deck_spec.json`, 목적, 청중, 필수 보존 수치·문구와 사용한 출처 목록이다. 출처가 필요한 주장인데 근거가 없으면 이 스킬이 새 사실을 만들지 않고 상위 에이전트에 보완을 요청한다.

기존 PPTX의 SmartArt, OLE, 복잡한 차트, 수식과 미디어처럼 Python에서 안정적으로 재작성하기 어려운 객체는 편집 가능 상태로 보존하지 않아도 된다. 내용과 시각을 추출할 수 있으면 `deck_spec.json`에 기록하고 결과에서는 이미지 또는 정적 요소로 평면화한다. 추출할 수 없는 객체는 원본 슬라이드 번호와 함께 경고한다.

### 폰트 배포와 사용

CI와 하나서체의 Windows용·macOS용 원본 ZIP을 저장소에 포함한다. `assets/fonts/windows/`와 `assets/fonts/macos/`로 나누고, `assets/fonts/manifest.json`에 정확한 ZIP 멤버·패밀리명·스타일을 기록한다. 실행 시 현재 OS와 덱에서 사용하는 스타일에 필요한 멤버만 작업 캐시에 풀고 `brand.json`의 논리 폰트 역할과 연결한다.

저장소 포함과 PPTX 폰트 임베딩은 별개다. `python-pptx`는 글꼴 이름만 기록하므로, 스킬은 저장소의 번들 폰트를 별도 후처리로 PPTX 내부에 임베딩한다. 정상적으로 임베딩된 PPTX는 수신자 PC에 해당 폰트가 설치되어 있지 않아도 데스크톱 및 웹 PowerPoint에서 임베디드 폰트를 사용할 수 있다. 다만 폰트의 임베딩 권한과 PowerPoint의 실제 인식 여부를 모두 검증한 결과만 성공으로 인정한다.

기본 출력 정책은 `embed-preferred`로 한다. `font_preflight.py`가 TTF/OTF 형식, 실제 패밀리명, 임베딩 권한 비트를 검사한 뒤 다음 경로를 선택한다.

1. `font_preflight.py`가 OpenType `OS/2.fsType`을 확인해 임베딩이 제한된 폰트를 차단하고, 실제 사용된 패밀리·스타일·글리프 목록을 만든다.
2. 검증된 임베딩 경로가 있으면 `embed_fonts.py`가 사용된 글리프만 서브셋으로 만들어 Regular/Bold 등 필요한 스타일별 폰트를 PPTX에 포함한다. 사용자가 직접 편집하지 않으므로 전체 문자 임베딩은 기본값으로 사용하지 않는다.
3. Windows 데스크톱 PowerPoint를 사용할 수 있으면 `SaveAs`/`SaveCopyAs`의 `EmbedFonts` 옵션과 `Font.Embedded` 상태를 이용하는 자동화 경로를 우선 검증한다. PowerPoint가 번들 폰트를 읽기 위해 설치가 필요한 환경에서는 사용자 승인 없는 영구 설치를 수행하지 않고, 검증된 임시·사용자 범위 등록 또는 OOXML 직접 임베딩 경로를 사용한다.
4. PPTX 패키지 내부에 폰트 데이터가 존재하는지만 확인하지 않는다. 결과를 PowerPoint에서 다시 열어 사용된 모든 필수 폰트가 임베딩 상태인지 검사하고, 폰트 미설치 검증 환경에서 PNG로 렌더링해 줄바꿈과 배치가 기준 범위 안인지 확인한다.
5. 임베딩 권한이 없거나 임베딩·재열기·렌더 검증 중 하나라도 실패하면 임베디드 PPTX를 성공 산출물로 제공하지 않고, 텍스트 또는 전체 슬라이드를 이미지로 고정한 `portable-static.pptx`를 생성한다.
6. 모든 경우에 레이아웃을 고정한 PDF와 검사용 PNG를 함께 생성한다. PDF를 시각 정합성의 배포 기준본으로 사용한다.

자동 시스템 폰트 설치는 권한과 로컬 상태를 변경하므로 명시적 승인 없이 수행하지 않는다. 수신자 PC에는 폰트 설치를 요구하지 않는다. OOXML 직접 임베딩은 Windows·macOS PowerPoint와 웹 PowerPoint에서 교차 검증되기 전에는 기본 성공 경로로 간주하지 않는다.

사용자가 직접 편집하지 않으므로 사용된 글리프만 포함하는 서브셋 임베딩을 기본값으로 삼고, 전체 글리프 임베딩과 편집 가능성은 완료 기준에서 제외한다. AI 재작업은 `deck_spec.json`에서 수행하며 문구가 바뀌면 새 글리프 서브셋을 만들어 전체 산출물을 재생성한다. 임베딩이 불가능한 경우에는 정적 PPTX도 허용한다.

### 품질 검사 수준

- 구조 검사: 색상, 폰트, 좌표, 로고, 콘텐츠 불변 조건을 결정적으로 검사
- 렌더 검사: 실제 PowerPoint를 우선 사용하고 LibreOffice를 대체 렌더러로 사용해 슬라이드별 PNG 생성
- 이미지 자동검사: 잘림, 겹침, 여백 부족, 정렬 이탈, 비정상 밀도와 슬라이드 간 위치 불일치 검사
- 비전 에이전트 검사: 시각적 위계, 균형, 브랜드 유사성, 표·차트 자연스러움과 AI 티 평가
- 사람 검사: 자동 반복 3~5회 후 최종 결과 승인

렌더러가 없는 환경에서는 텍스트 오버플로우를 근사 휴리스틱으로 검사하고 결과를 `warning`으로 낮춘다. 렌더링 기반 시각 검사를 수행하지 못한 결과는 최종 `pass`가 아니라 `partial`로 보고한다.

## 범위 밖

- SVG 기반 중간 표현
- 라이브 프리뷰 웹서버
- 복잡한 다단계 승인 UI
- 동적 브랜드 플러그인 시스템
- 폰트와 이미지 라이선스 재검토
- Claude 또는 Codex 전용 API를 핵심 실행 경로에 포함하는 작업

## 주요 위험과 대응

| 위험 | 대응 |
|---|---|
| 샘플 간 스타일이 서로 다름 | 최신/정식 샘플에 우선순위를 주고 빈도와 예외를 함께 기록 |
| 자동 슬라이드 분류 오류 | 신뢰도와 근거를 남기고 애매한 항목은 `unclassified` 처리 |
| 테마색·상속색 추출 누락 | 직접 RGB뿐 아니라 테마/마스터/레이아웃 상속을 별도 처리 |
| 텍스트 오버플로우 오판 | 휴리스틱 점수와 한계를 리포트에 명시하고 시각 검사 병행 |
| LibreOffice와 PowerPoint 렌더링 차이 | PowerPoint 결과를 최종 기준으로 삼고 사용한 렌더러를 리포트에 기록 |
| 비전 평가의 비결정성 | 정량 검사와 고정된 시각 평가 루브릭을 함께 사용하고 실패 근거를 구조화 |
| `SKILL.md`와 `AGENTS.md` 드리프트 | 생성 또는 동기화 검증을 테스트에 포함 |
